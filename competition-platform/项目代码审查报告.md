# 竞赛组队平台 — 代码审查报告

> 审查范围：后端 Java + 前端 Vue + 数据库 schema + 配置文件，共 60+ 个源文件

---

## 一、整体评价

项目完成度较高，功能模块覆盖了技术方案中的全部核心模块（用户认证、队伍管理、AI 推荐、实时聊天、成就展示、管理后台等）。架构清晰，分层合理（Controller → Service → Mapper），使用了 JWT + Redis 黑名单的认证方案，AI 推荐有 LLM 增强 + 规则引擎降级设计。但在安全性、性能、代码质量和细节上存在若干需要调整的问题。

---

## 二、严重问题（建议优先修复）

### 1. 文件上传缺少认证（严重安全漏洞）

**文件**: `FileController.java`

文件上传接口 `/api/files/upload` 没有任何认证检查——不需要登录即可上传文件。这意味着任何人都可以向服务器上传文件，可能被滥用进行存储攻击或上传恶意文件。

**建议**：
- 添加 `@PreAuthorize("isAuthenticated()")` 或在 SecurityConfig 中对 `/api/files/**` 设置 `authenticated()` 规则
- 增加文件大小总量限制（目前仅靠 Spring 的 `max-file-size`，但无防刷机制）

### 2. 文件上传路径遍历风险

**文件**: `FileController.java`

```java
private final Path uploadDir = Paths.get("uploads").toAbsolutePath();
// ...
file.transferTo(uploadDir.resolve(filename).toFile());
```

虽然文件名使用了 UUID 重命名（已大幅降低风险），但 `originalName` 直接返回给前端，如果 `originalName` 包含恶意脚本内容，配合 XSS 可能造成问题。此外 `uploadDir` 使用相对路径，在不同启动目录下行为不一致。

**建议**：
- `uploadDir` 改为配置项，使用绝对路径
- 对 `originalName` 做清洗（去除路径分隔符等特殊字符）

### 3. JWT Secret 硬编码兜底值

**文件**: `application.yml`

```yaml
secret: "${JWT_SECRET:campus-competition-platform-jwt-secret-key-2026-please-change-in-prod-0123456789}"
```

虽然用了环境变量注入，但提供了可猜解的默认值。如果部署时忘记设置环境变量，攻击者可以用这个已知密钥伪造任意 JWT。

**建议**：去掉默认值，启动时强制检查 `JWT_SECRET` 环境变量，未设置则启动失败。

### 4. 数据库密码默认值

**文件**: `application.yml`

```yaml
password: "${DB_PASSWORD:123456}"
```

默认密码 `123456` 是弱密码。虽然是毕业设计，但如果部署到服务器上会存在风险。

**建议**：在 `.env.example` 和文档中强调修改默认密码；生产部署去掉默认值。

### 5. AI 推荐全表扫描性能问题

**文件**: `AiService.java`

```java
for (User user : userMapper.selectList(null)) {
```

推荐逻辑遍历**全部用户**进行逐个匹配计算。当用户量增大（>1000）时会导致严重性能问题，且每个用户还要查询技能和成就表，造成 N+1 查询。

**建议**：
- 使用数据库层面筛选（只查询 `compete_status IN ('WANT_INVITE','ACCEPT_INVITE')` AND `role='STUDENT'` 的用户）
- 批量查询用户技能，减少 N+1 查询
- 考虑加缓存

## 三、中等问题

### 6. 缺少分页（队伍广场）

**文件**: `TeamController.java` / `TeamService.java`

根据技术方案文档描述"队伍广场支持分页+筛选"，但实际代码中 `TeamService.search()` 返回 `List<TeamVO>` 而非分页对象，没有分页逻辑。

**建议**：改用 MyBatis-Plus 的 `Page` 分页，返回 `PageVO<TeamVO>`。

### 7. 队伍成员数实时性 — N+1 查询

**文件**: `TeamService.java` 中 `toTeamVO` 方法

队伍成员数通过单独查询 `teamMemberMapper.selectCount()` 获取，在列表展示多个队伍时产生 N+1 查询。

**建议**：使用 JOIN 或子查询一次性获取所有队伍的成员数。

### 8. 用户列表 N+1 查询

**文件**: `FollowService.java`

```java
.stream().map(f -> userMapper.selectById(f.getFolloweeId()))
```

关注/粉丝列表中，对每个 Follow 记录单独查询 User，是典型 N+1 问题。

**建议**：先批量获取所有用户 ID，再使用 `selectBatchIds()` 一次性查询。

### 9. 团队讨论区列表反转方式

**文件**: `TeamDiscussionService.java`

```java
java.util.Collections.reverse(result.getRecords());
```

在内存中反转分页结果列表，这种方式在数据量大时效率低，且语义不够清晰。

**建议**：直接按 ID 升序查询，或使用前端排序。

### 10. 缺少参数校验注解

多个 DTO 缺少完整的校验：

- **`CompetitionReq.java`**: `signupStart`/`signupEnd`/`startTime` 使用 String 而非 LocalDate，且无日期格式校验
- **`TaskCreateReq.java`**: `deadline` 使用 String，无格式校验
- **`TeamCreateReq.java`**: 需检查是否有队伍人数上限校验

**建议**：
- 日期字段改用 `@DateTimeFormat` + `LocalDate`
- 添加 `@Size`、`@Max` 等约束注解
- Controller 中添加 `@Valid` 注解

### 11. ContentFilterService 词库硬编码

**文件**: `ContentFilterService.java`

内容过滤词库直接硬编码在代码中，修改需要重新编译部署。

**建议**：将词库放到数据库表或配置文件中，支持动态更新。

### 12. ChatWebSocketHandler 消息持久化

需要确认 WebSocket 聊天消息是否持久化到数据库。如果仅在内存中保存，重启后消息丢失。

### 13. 静态资源映射不完整

**文件**: `WebConfig.java`

需要确认是否配置了 `/uploads/**` 的静态资源映射，否则上传的文件无法通过 URL 访问。

## 四、轻微问题 / 代码质量

### 14. Entity/DTO/VO 样板代码冗长

所有 Entity 和 DTO 都使用传统的 getter/setter，代码冗长。项目已使用 Lombok（pom.xml 中有依赖），但 Entity 类中仍手写 getter/setter。

**建议**：统一使用 `@Data`、`@Getter`、`@Setter` 注解。

### 15. 异常处理可细化

**文件**: `GlobalExceptionHandler.java`

需要确认是否处理了以下异常：
- `MaxUploadSizeExceededException`（文件超限）
- `HttpMessageNotReadableException`（请求体解析失败）
- `AccessDeniedException`（权限不足）

### 16. 前端 API 响应类型缺失

**文件**: `frontend/src/api/index.js`

前端 API 使用纯 JS，没有 TypeScript 类型定义。建议至少使用 JSDoc 注释标注返回类型。

### 17. 前端 WebSocket 重连机制

**文件**: `frontend/src/utils/websocket.js`

需要确认断线重连逻辑是否完善（指数退避、最大重试次数等）。

### 18. 前端路由守卫可细化

**文件**: `frontend/src/router/index.js`

需要确认是否有管理员路由守卫（非管理员访问 `/admin` 时跳转）。

### 19. 前端 store 持久化

需要确认 `stores/user.js` 在页面刷新后是否持久化（localStorage），否则用户登录状态会丢失。

### 20. 竞赛方向匹配过于简单

**文件**: `AiService.java`

```java
if (name.contains("数学建模")) {
    keywords.add("数据分析");
    keywords.add("机器学习");
    keywords.add("文档写作");
}
```

竞赛方向匹配仅靠硬编码关键词，只覆盖了三种竞赛类型。对于其他竞赛，直接给 12 分。

**建议**：可以从竞赛描述中提取关键词，或让管理员维护竞赛-技能映射表。

## 五、数据库设计问题

### 21. schema.sql 外键约束

需要检查 `schema.sql` 中表是否设置了外键约束，还是仅靠逻辑层面关联。毕业设计中可以接受逻辑外键，但应确保所有删除操作处理了级联关系。

### 22. 缺少索引

需要确认以下高频查询字段是否有索引：
- `team_application.team_id` + `status` 联合索引
- `team_member.team_id` 索引
- `follow.follower_id` 和 `follow.followee_id` 索引
- `team_discussion.team_id` 索引

### 23. 软删除缺失

用户、队伍等核心实体没有软删除字段（`is_deleted`/`deleted_at`），物理删除可能导致关联数据不一致。

## 六、与技术方案的设计差异

### 24. 缺少"邀请"功能

技术方案中提到了"邀请加入"功能，但代码中仅实现了"申请加入"。需要确认队长主动邀请用户加入的逻辑是否实现。

### 25. 缺少通知推送渠道

技术方案提到多种通知类型，需要确认：
- 申请被同意/拒绝时是否自动发通知
- 队长收到新申请时是否通知
- WebSocket 是否用于实时通知推送

### 26. 成就审核流程

`AchievementReq.java` 注释提到"经管理员审核后公开"，需要确认 `AchievementService` 中是否实现了审核状态流转逻辑。
